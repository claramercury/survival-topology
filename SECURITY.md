# Security Policy for Survival Topology

As a theoretical control theory framework for General Intelligence, the Survival Topology repository currently operates purely in the domain of architectural and philosophical modeling (the "Wh- Protocol").

While this repository (`main` branch) does not contain an active, deployed application, we take the security of its concepts, documentation, and conceptual implementations seriously.

## Supported Versions

| Version | Supported          | Notes                                         |
| ------- | ------------------ | --------------------------------------------- |
| 1.0     | :white_check_mark: | Initial theoretical draft framework.          |
| < 1.0   | :x:                | Pre-release notes and drafts are unsupported. |

## Conceptual Security Principles

The **Survival Topology** architecture introduces security at its foundation through the "Wh- Protocol", designed to prevent standard AI failure modes (hallucinations, unaligned agency):

- **Identity Integrity (WHO / Gravity):** Securing the static definition of "Self" to prevent prompt injection or identity drift.
- **Pain Feedback (WHAT / Error):** Ensuring the system reliably penalizes deviations from reality, closing the loop on malicious subversions.
- **Counterfactual Safety (WHICH / Simulation):** Sandboxed "death" simulations before action execution.

If you discover a theoretical vulnerability where the 7 dimensions fail to constrain an agent, or a practical vulnerability in our simulation scripts or documentation infrastructure, we encourage you to report it.

## Reporting a Vulnerability

**DO NOT** create a public issue for any security vulnerability, either conceptual (flaws in the control theory that could lead to unaligned actions) or technical (e.g., malicious pull requests targeting our documentation pipeline).

Please follow these **private responsible disclosure** practices:

1. **Private Reporting:** Report vulnerabilities directly to the repository maintainer through GitHub's private vulnerability reporting feature (if enabled for this repository) or through secure, private communication channels provided by the maintainer.
2. **Provide Details:** Include a clear description of the vulnerability, the potential impact, and steps to reproduce or theoretically prove the flaw.
3. **Assessment:** The maintainer will acknowledge receipt, assess the severity (CRITICAL/HIGH/MEDIUM/LOW), and begin developing a mitigation or patch.
4. **Resolution:** We aim to address conceptual and technical security issues promptly and will provide updates to the reporter throughout the process.

Public disclosure of vulnerabilities should only occur after a fix has been successfully implemented and merged.
